# P3b — MCP Server for AI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An AI client (Claude Code, Claude Desktop, …) connected to `https://zentask-api.vuhpquang.com/mcp`
can search, create, edit, complete, trash and delete tasks and tags, as if it were one more device.

**Architecture:**
- The server hosts an **MCP replica**: a `ZenStore` (the same client database code) at
  `<dataDir>/mcp.db`, with its own HLC node.
- Every tool call does three steps, all serialised by one mutex:
  1. pull everything newer from `ServerDb` into the replica (`applyRemote`);
  2. run the shared `TaskActions` / `TagActions` / `TaskIndex` on the replica;
  3. push the replica's outbox into `ServerDb.apply`.
- MCP edits therefore follow exactly the same rules as the app: per-field LWW, recurring copies, Trash.
  Devices receive them on their next sync. There is no second write path.
- The MCP protocol is JSON-RPC 2.0 over **Streamable HTTP** (`POST /mcp`, JSON responses), implemented
  directly. It needs only `initialize`, `notifications/initialized`, `ping`, `tools/list` and `tools/call`.

**Tech Stack:** Ktor server (existing), kotlinx.serialization, shared `ZenStore` on the JVM (SQLDelight
sqlite-driver, already in `shared`'s jvmMain).

**Spec:** `docs/superpowers/specs/2026-11-08-zentask-design.md` §10a (MCP), §8 (auth), §7 (sync).

## Global Constraints

- Auth: `Authorization: Bearer <device token>`, the same tokens as `/v1` and the same `deviceBearer`.
  No token → 401. Tokens are revocable via `DELETE /v1/devices/{id}`.
- "Delete" means Trash by default. A permanent delete only happens with `permanent: true` on a task that
  is already in Trash, through `TaskActions.deleteForever`.
- Every successful write tool appends an audit row (`mcp_audit`) with the time, device id, tool,
  arguments, and the affected task ids with before/after JSON.
- Rate limit: 120 tool calls per minute per device. Beyond that, a JSON-RPC error `-32029` with the
  message "Too many requests".
- Input validation:
  - priority ∈ {0,1,3,5}, or names ("high"…);
  - dates are ISO 8601 (`2026-11-09`, `2026-11-09T09:00`, with an optional offset) in the zone given
    by `timezone` (default `Asia/Ho_Chi_Minh`);
  - titles are at most 500 characters;
  - unknown ids → a tool error result (`isError: true`) with a clear message, not a protocol error.
- Tool results are short JSON-like text the model can read: task `id`, `title`, `list`, `due`,
  `priority`, `tags`, `status`, `url` (none). Never dump raw records.
- The server binds and the tunnel are unchanged. Deploy with `scripts/deploy.sh` (allowed without asking).

## Rulings made while planning

- **MCP protocol implemented directly**, not with the `io.modelcontextprotocol:kotlin-sdk` (0.16.0). The
  subset we need is small and fully testable with `testApplication`. Pinning the SDK to Ktor 3.6 /
  Kotlin 2.4 is a risk for no gain. `Mcp-Session-Id` is issued on initialize and accepted but not
  required; the server is stateless per request apart from the replica. Protocol version: echo the
  client's version if it is one we know (`2025-06-18`, `2025-03-26`), otherwise `2025-06-18`.
- **Replica rather than server-side TaskActions on raw records:** this reuses every shared rule and
  test. Cost: one extra SQLite file on the server, and a pull/push per call (a few ms).
- **Tool set for P3b** (spec §10a):
  - `search_tasks`, `get_task`, `create_task`, `update_task`, `complete_task`, `reopen_task`,
    `wont_do_task`, `trash_task`, `restore_task`, `delete_task`
  - `add_subtask`, `add_checklist_item`, `set_checklist_item`
  - `list_lists`, `list_tags`, `rename_tag`, `set_tag_color`, `delete_tag`
  - `create_task` also accepts `quick_add` (the same parser as the app: `#tag !high ^list tomorrow 9am`).
  - The list/habit/countdown/event tools come with P4/P5/P6.

## Review Focus

1. A tool call while a device syncs concurrently: no lost update. The replica pull happens before the
   action, and pushes go through `ServerDb.apply` (merge), not an overwrite.
2. A token revoked between calls → 401 on the next call.
3. `delete_task` without `permanent` never tombstones. With `permanent` on a task not in Trash, it errors.
4. Garbage JSON-RPC, a missing `id`, unknown methods, unknown tools, wrong argument types → proper
   JSON-RPC errors or `isError` results, never a 500.
5. Audit rows exist for every write and none for reads.

### Task 1: MCP replica (server)

**Files:**
- Create: `server/src/main/kotlin/com/vuhpquang/zentask/server/mcp/McpReplica.kt`.
  It exposes `class McpReplica(db: ServerDb, file: Path, now: () -> Long)` with
  `suspend fun <T> transact(block: (ZenStore, TaskActions, TagActions, TaskIndex) -> T): T`.
  `transact` holds a mutex and does: pull → block → push. The pull pages `changesSince(replicaCheckpoint)`
  until `hasMore` is false. The push is `pending → db.apply → markSynced`. A `serverId` change resets the
  checkpoint.
- Modify: `ServerDb`. Add `changesSince` reuse (exists) only; no schema change.
- Test: `McpReplicaTest`:
  - `seesDeviceChangesBeforeActing`
  - `pushesActionsToServerDb`
  - `concurrentDeviceEditOfAnotherFieldSurvives`
  - `restoredServerIdResetsReplica`
- Commit `feat(server): MCP replica store synced in-process with ServerDb`.
