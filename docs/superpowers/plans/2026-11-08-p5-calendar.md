# P5 — Calendar Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Calendar area (rail ⌘2) with Day, Week and Month views that shows tasks and Google Calendar
events from several accounts (personal and work), read-only.
- In Week and Day, all-day items sit in the top row; there is an hour grid with a "now" line.
- A panel lists tasks that can be dragged onto the grid to give them a time.
- An iCal secret URL works as the fallback when an account blocks OAuth.

**Architecture:**
- **The server owns calendars.** Google OAuth runs on the server. Refresh tokens are encrypted with
  AES-GCM and stored in a server-only table `calendar_credentials`; they are never synced.
- A sync job runs every 10 minutes:
  - it reads each account's calendar list and events (90 days back to 365 days ahead, `singleEvents=true`);
  - it writes `CalendarAccount` / `CalendarSource` / `CalendarEvent` records into `ServerDb` through
    `apply` with a server HLC node;
  - devices receive those records through normal `/v1/sync`.
- The client is read-only for calendar records. Which calendars are shown is a client `Preference`
  (`calendar.hidden` = list of source ids).
- **The connect flow:**
  1. The app calls `POST /v1/calendar/google/start` (authenticated) and receives a one-time
     `https://accounts.google.com/…&state=<random>` URL. The state expires after 10 minutes and is
     bound to the device.
  2. The app opens that URL in the browser.
  3. Google redirects to `GET /v1/calendar/google/callback` (public; it checks `state`). The server
     exchanges the code, stores the encrypted refresh token, creates the account, syncs once, and
     shows a small "Connected — you can close this tab" page.
- **iCal:** `POST /v1/calendar/ical {name, url}` adds an ICAL account. The server fetches the feed every
  15 minutes and parses VEVENTs (DTSTART/DTEND/SUMMARY/LOCATION/DESCRIPTION; RRULE expanded with the
  shared `Recurrence` subset, plus EXDATE).
- **Shared `calendar/`:** `CalendarQueries` (events and tasks per day for a range, `isAllDay` handling)
  and `DayLayout` (overlap columns for timed items).
- **macOS `Calendar/`:** `CalendarModel`, `WeekView`, `DayView` (WeekView with one column), `MonthView`,
  `TaskPanel` (drag source), and Settings → Calendars (connect Google, add iCal, list accounts with a
  visibility toggle per calendar, remove an account).

**Spec:** §3 (priority 3), §5, §6 (Calendar* entities), §9 (Google Calendar), §11 (Calendar UI). Setup
guide §3 (Google OAuth, done by the owner) and §4 (iCal).

## Global Constraints

- Scope: `https://www.googleapis.com/auth/calendar.readonly`, plus `openid email` to show which account.
  `access_type=offline`, `prompt=consent`. Redirect URI `${ZENTASK_PUBLIC_URL}/v1/calendar/google/callback`.
- Secrets: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` and `ZENTASK_ENCRYPTION_KEY` (32 bytes, base64)
  come from `.env`.
  - Without the client id or secret, Google connect returns `503 google_not_configured`.
  - Without the key, the server refuses to store tokens.
- Calendar records are server-owned: `/v1/sync` keeps rejecting client writes to them (P1).
- Removing an account deletes its credentials and tombstones its account, sources and events.
- Never log tokens, codes or the encryption key.
- UI follows `feedback-zentask-ui-size`: big targets, the rail, light and dark. Events are read-only;
  tasks can be dragged.

## Rulings made while planning

- **Visibility is a client Preference** (`calendar.hidden`), not the spec's client-editable
  `CalendarSource.visible` field. Server-owned records stay entirely server-written, which is simpler
  and safer. Cost: visibility is per user, not per source record. That is the same thing for one user.
- **Full window refresh every 10 minutes**, not incremental `syncToken`. A personal account has a few
  hundred events in the window. The diff writes only changed events and tombstones vanished ones.
  `syncToken` can come later if quota or latency matters.
- **The Week view starts on Monday**, the Vietnamese convention. A synced Preference
  `calendar.weekStart` changes it later.

## Review Focus

1. A refresh token is never written in clear text anywhere: not in a record, a log or a response.
2. A forged or expired `state` on the callback never creates an account.
3. An event deleted or moved in Google disappears from or moves in ZenTask after the next sync. An
   unchanged event writes nothing (no version churn).
4. All-day events (`date`, not `dateTime`) land on the right local day in UTC+7, including multi-day
   events.
5. A Google API failure (revoked grant → `invalid_grant`, 5xx, quota) marks the account
   `needs_reconnect` or retries later. It never wipes the account's events.

### Task 1: Server — credentials, OAuth flow, Google client

- `server/.../calendar/Crypto.kt`: AES-GCM encrypt/decrypt with a 12-byte random nonce; the key comes
  from config.
- `ServerDb`:
  - add `calendar_credentials(account_id PK, provider, email, secret_enc, created_at, status)`;
  - add `oauth_states(state PK, device_id, created_at)`;
  - add a `serverClock` (an `HlcClock` with node `server`) for writing records.
- `GoogleApi(http, clientId, clientSecret)`: `authUrl(state, redirect)`, `exchange(code)`, `refresh(refreshToken)`,
  `calendarList(access)`, `events(access, calendarId, timeMin, timeMax)` (paged), and `userEmail(access)`.
- Routes `POST /v1/calendar/google/start` (auth) and `GET /v1/calendar/google/callback` (public HTML).
- Tests, with a MockEngine Google:
  - crypto round trip, plus a wrong key fails
  - start returns a URL with a state; the callback with a good state stores an encrypted secret and
    creates the account and its sources
  - a bad or expired state → 400 page, nothing stored
  - the DB file does not contain the refresh token
  - missing config → 503

### Task 2: Server — sync job and iCal

- `CalendarSync` (runs on a coroutine timer; `syncNow(accountId)` for tests):
  - Google: refresh the access token, then the calendar list, then events per source. Map them to
    records (ids `gcal_<accountId>_<eventId>`), diff against stored records, and apply only changes.
    Missing events in the window → tombstone.
  - iCal: fetch, parse, expand, and do the same diff.
- Map event times. Timed events use the instant. All-day events use local midnight in the calendar's
  zone, with `isAllDay` set and `end` exclusive.
- Error handling: `invalid_grant` → account `status = needs_reconnect`, events kept. Other errors → retry
  on the next tick.
- Routes `POST /v1/calendar/ical` and `DELETE /v1/calendar/accounts/{id}` (auth).
- Tests:
  - the first sync creates events, and a second identical sync writes 0 records
  - a moved or deleted event
  - an all-day multi-day event in UTC+7
  - `invalid_grant` keeps events
  - iCal parse (folded lines, TZID, all-day, RRULE weekly + EXDATE)
  - removing an account tombstones everything

### Task 3: Shared — calendar queries and layout

- `CalendarQueries.items(index, events, from, to, zone, hidden)` → `Map<LocalDate, DayItems(allDay, timed)>`.
  Items are `CalendarItem.Event` / `CalendarItem.TaskItem` with a start, an end and a colour.
  - Tasks with a time last 30 minutes by default; tasks with start+due use the range.
  - Completed tasks show struck through.
- `DayLayout.columns(timed)` → each item with a (column, columnCount) for overlaps.
- Core: `calendarItems(from, to)`; `hiddenCalendars()` / `setHidden(sourceId, hidden)` (Preference);
  `startGoogleConnect(): String` (calls start); `addIcal(name, url)`; `removeCalendarAccount(id)`.
- Tests: grouping across midnight and multi-day, hidden sources, overlap columns, and the task default
  duration.

  - accounts with status (and a "Reconnect" button when it needs reconnecting);
  - calendars with visibility toggles and colour dots;
  - "Add iCal link…";
  - "Remove account" with a confirmation.
- Tests: CalendarModel range math (week start Monday, prev/next, month grid of 6 weeks), drop → `setDue`,
  snapshots light and dark, `design-check`.
