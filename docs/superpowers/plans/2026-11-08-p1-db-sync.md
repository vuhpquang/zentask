# P1 — Database + Sync Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Offline-first local database for every entity in spec §6, per-field LWW sync through an
authenticated `POST /v1/sync` on the server, proven by two test clients converging through a real
in-process server.

**Architecture:** Typed Kotlin models (one `@Serializable` data class per entity) are converted to and
from a generic *field map* (`Map<String, JsonElement>`) by kotlinx.serialization. Sync, merge and storage
all work on that field map plus a per-field HLC clock map (`SyncRecord`). That means one merge
implementation, no per-entity sync code, and new fields never need an SQL migration. The client stores
records in SQLDelight (`record`, `pending_change` outbox, `sync_meta`). The server stores the same records
in SQLite over JDBC, with a global `version` counter.

**Tech Stack:** Kotlin 2.4.20 MPP (jvm + macosArm64), SQLDelight 2.4.1 (native-driver / sqlite-driver,
coroutines-extensions; spiked 2026-11-08: JVM + native tests and XCFramework OK), kotlinx.serialization
1.12.0, coroutines 1.11.0 (+ coroutines-test), Ktor 3.6.1 client (core, darwin, cio, mock) and server
(+ auth), sqlite-jdbc 3.54.1.0 on the server.

**Spec:** `docs/superpowers/specs/2026-11-08-zentask-design.md` (§6 data model, §7 sync, §8 auth).

## Global Constraints

- Offline first: every write goes to the local DB **and** the outbox in one transaction (spec §7).
- Merge = per-field last-writer-wins on HLC; deletion = tombstone field `deleted=true`; Trash =
  `trashedAt`, separate from `deleted` (§7, §7.1). List fields (`tags`, `reminders`) merge as one field (§7.1).
- Priority values 0/1/3/5, task status 0/2/-1 (+ TickTick's legacy 1 kept as-is), exactly as §6.
- Every server endpoint except `/health`, `/`, `/privacy`, `/terms` and `POST /v1/auth/login` needs
  `Authorization: Bearer <device token>` (§8). Device tokens are stored hashed (SHA-256).
- Server binds `127.0.0.1` unless `HOST` says otherwise (the container sets `HOST=0.0.0.0`; compose still
  publishes only `127.0.0.1:3100`).
- Persisted names are a file format: entity names, field names (`@SerialName`/property names) and
  `sync_meta` keys are never renamed once shipped.
- `shared` stays platform-free; `expect/actual` only for the SQLite driver.
- Anti-goal (blocker): sync must never lose or silently overwrite data. Any path that could, gets a test.
- Run Gradle through `scripts/lib/env.sh` (Corretto 17 arm64). Commit + push `main` after each task.

## Rulings made while planning (builder's calls, the owner can change them)

- **Generic record storage**, not one SQL table per entity. Why: sync needs field maps anyway; a newer
  client's unknown entity/fields survive on older clients; adding a field is not a migration. Cost: list
  queries decode JSON in Kotlin. That is fine at a few thousand tasks. If it ever isn't, add typed shadow
  tables or expression indexes.
- **Enum-like fields are `Int`/`String` with constants**, not Kotlin enums, so an unknown value written by
  a newer client still decodes.
- **The fixed Inbox id is `"inbox"`**, so two devices never create two Inboxes.
- **Tombstone purge (>90 days) is deferred.** Purging needs a "full resync" protocol to avoid resurrecting
  records on long-offline clients. Tombstones are tiny. Noted in the spec.
- **Server echo:** the pull half of a sync may return records the client just pushed. Merge is idempotent,
  so the client writes nothing. This is simpler than the spec's "exclude unchanged" optimisation.
- **Password:** the server keeps only a PBKDF2-HMAC-SHA256 hash of `ZENTASK_PASSWORD` in memory (JDK
  built-in, no extra dependency). Login is rate-limited globally: 5 failures per 15 minutes gives 429.
  It is global because every request arrives through cloudflared, so client IPs are not meaningful.
- **Server identity:** the server DB gets a random `serverId` when it is created. A client that sees a
  different `serverId` than last time (DB restored or recreated) resets its checkpoint and re-uploads
  every local record. Without this, records would silently exist only on that client.
- **Clock-skew guard:** the server rejects changes whose HLC is more than 24 h ahead of server time
  (`400 clock_skew`). Otherwise one bad clock would make that field uneditable until real time catches up.

## Review Focus

1. An edit made while a sync request is in flight must stay in the outbox (seq check), not be cleared by
   that request's success.
2. A failed or unauthorized sync keeps the outbox intact and the checkpoint unchanged.
3. Records the client cannot decode: an unknown entity, or a field of the wrong type from a newer
   client. They must be stored and kept, never dropped or crash `list()`.
4. Pagination boundary: pulling exactly 500, 501 and 1200 records ends with every record present and
   `hasMore=false`.
5. Auth edges: a revoked token gives 401, a missing/garbage header gives 401, the 6th wrong password
   within 15 min gives 429 even if correct afterwards inside the window, and no endpoint under `/v1`
   (other than login) is reachable without a token.

### Task 6: Client SyncApi, SyncEngine, SyncScheduler + end-to-end

**Files:**

- Test: `shared/src/commonTest/kotlin/com/vuhpquang/zentask/sync/SyncEngineTest.kt` (Ktor `MockEngine`),
  `SyncSchedulerTest.kt` (`runTest` virtual time)
- Test: `server/src/test/kotlin/com/vuhpquang/zentask/server/SyncEndToEndTest.kt` (two `ZenStore`s on
  in-memory drivers ↔ `testApplication` server through `createClient`)

**Interfaces:**
- Consumes: Task 3 `ZenStore` sync-facing API; Task 4/5 protocol and routes.
- Produces:
  - `class SyncApi(http: HttpClient, baseUrl: String, token: () -> String?)`:
    - `suspend fun login(password, deviceName): LoginResponse`.
    - `suspend fun sync(req: SyncRequest): SyncResponse`.
    - It encodes and decodes with `ZenJson` itself, so no client plugin is required.
    - It throws `SyncException(val kind: SyncErrorKind)`, where `SyncErrorKind` is
      `UNAUTHORIZED | NETWORK | SERVER | CLIENT`.
  - `class SyncEngine(store: ZenStore, api: SyncApi, pushBatch: Int = 200)`:
    - `val status: StateFlow<SyncStatus>`.
    - `suspend fun syncOnce(): SyncStatus`. It is serialised by a Mutex, so concurrent calls run one
      after another.
  - `sealed interface SyncStatus`:
    - `Idle`
    - `Syncing`
    - `Synced(at: Long)`
    - `Failed(kind: SyncErrorKind, message: String)`
  - Algorithm: loop
    1. Take `pending(pushBatch)` and send it with the current checkpoint.
    2. On success: `markSynced`, `applyRemote(resp.changes)`, then set the checkpoint.
    3. If `resp.serverId != store.serverId` and the stored one is not null: `markAllPending()`, set
       checkpoint 0, continue. Store the serverId.
    4. Repeat while there is pending work or `hasMore`.
